# Harness-Search: Qwen/Gemma Search Agent Adaptation

## Source: harness-1 (Pengcheng Jiang et al., 2026)

Paper: arXiv 2606.02373
Repo: https://github.com/pat-jj/harness-1
HF: https://huggingface.co/pat-jj/harness-1

### What harness-1 Is

A **20B search agent** trained with RL inside a stateful retrieval harness. The harness maintains recoverable search state: candidate documents, curated evidence, evidence links, verification records, and budget-aware context. The policy makes semantic decisions: what to search, which documents to inspect or curate, what claims to verify, and when evidence is sufficient.

**Key architectural decisions:**
- GPT-OSS MoE: 24 layers, 32 experts (top-4 routing), hidden=2880, ~3B active/token
- Hybrid attention: sliding window (128) + full attention alternating
- Yarn RoPE: 131K max context (scaled from 4K base)
- Harmony/GPT-OSS token encoding: multi-channel output (analysis/commentary/final)
- Raw token-ID prompts via /v1/completions (no chat template)

### Search Harness State

```
WorkingMemory:
  curated_docs: dict[id -> Document]      # selected as evidence
  candidate_pool: dict[id -> Document]     # found but not yet curated
  search_history: list[SearchResult]       # past queries + results
  verification_records: list[Verification]  # fact-checking results
  evidence_links: dict[id -> list[id]]      # doc -> supporting docs
  token_budget: int                         # remaining context budget
```

### Tool Set

| Tool | Description |
|------|-------------|
| fan_out_search(queries) | Up to 5 parallel diverse searches |
| search_corpus(query) | Single hybrid semantic+keyword search |
| grep_corpus(pattern) | Exact regex matching |
| read_document(doc_id) | Full document text |
| review_docs(doc_ids) | Re-read from memory (free) |
| curate(add_ids, remove_ids, importance) | Manage curated set |
| verify(doc_ids, claim) | Check if docs support claim |
| end_search(reasoning) | Submit final curated set |

### Training Recipe (RL)

1. **SFT phase**: Teacher-forcing on expert search trajectories
   - Generated by driving GPT-4/Claude with full tool access
   - Replayed through WorkingMemory for context assembly
   
2. **RL phase**: REINFORCE with Tinker
   - Reward = recall_beta * (outcome_weight * recall + trajectory_weight * traj_recall + final_answer_bonus) - format_penalty - gap_penalty - turn_penalty
   - Stride=5 non-overlapping windows for full coverage
   - Context: 32K token window, 2K generation budget

### Key Design Patterns

1. **State externalization**: All search state is recoverable from trajectory - no hidden LM state
2. **Search -> curate rhythm**: Model must curate after every search (enforced by nudge prompts)
3. **Budget awareness**: Token budget tracked and communicated to model
4. **Backtracking**: Multi-step reasoning when search is stuck

## Qwen3 Adaptation

### Why Qwen3.6

**Already deployed on Mac Studio via oMLX:**
- Qwen3.6-27B-OptiQ-4bit (27B dense, 4-bit quantized, 256K context)
- Qwen3.6-35B-A3B-4bit (35B MoE with 3B active, 4-bit, 256K context)
- Both models: OpenAI-compatible API on port 9393, thinking mode, tool calling

**Advantages over harness-1 base:**
- 256K native context (vs 131K Yarn-scaled)
- Standard chat template + function calling (no custom Harmony encoding)
- Already quantized and deployed — zero setup needed
- Apache 2.0 license
- 27B dense or 35B MoE — comparable active params to harness-1's 20B MoE

### Architecture Changes from harness-1

| Component | harness-1 | Qwen3 Adaptation |
|-----------|-----------|-----------------|
| Base model | GPT-OSS MoE 20B | Qwen3-8B dense |
| Context | 131K (Yarn RoPE) | 128K (native) |
| Encoding | Harmony GPT-OSS | Qwen3 chat template |
| Prompt format | Raw token IDs | apply_chat_template |
| Tool format | Multi-channel JSON | Qwen function-calling |
| Serving | vLLM / Tinker | vLLM / SGLang |
| Training | Tinker REINFORCE | TRL GRPO / DPO |

### Why This Works Better Than harness-1

1. **No custom encoding**: Qwen3 uses standard function-calling JSON, no Harmony/GPT-OSS parser needed
2. **Smaller, faster**: 8B dense vs 20B MoE but comparable active params (~3B vs 8B)
3. **Better ecosystem**: LoRA adapters, dev-friendly, easy deployment
4. **Real training recipe**: Can use TRL/GRPO on consumer GPUs

## Implementation Plan

### Phase 1: Search Harness (Python package)

```
qwen-search-harness/
  harness/
    __init__.py
    state.py           # WorkingMemory class
    tools.py           # Tool definitions + Qwen function-calling schemas
    trajectory.py      # Action/Observation/Trajectory
    context.py         # Context assembly (token budget, windowing)
    prompts.py         # System prompt + nudge templates
    evaluate.py        # Recall/precision metrics
  training/
    sft_data.py        # SFT data generation (trajectory replay)
    train_sft.py       # LoRA SFT training
    reward.py          # Recall reward function
    train_rl.py        # GRPO / REINFORCE training
  inference/
    serve.py           # vLLM serving with tool loop
    local.py           # Local mlx_lm serving (Mac Studio)
```

### Phase 2: Training Data

Generate SFT trajectories by driving Qwen3-72B (or GPT-4o) through the search harness on a corpus. Save action/observation pairs.

### Phase 3: Training

1. SFT: LoRA fine-tune Qwen3-8B on 10K search trajectories
2. RL: GRPO fine-tune on 1K diverse queries with ChromaDB backend

### Phase 4: Evaluation

BrowseComp+ benchmark with:
- recall@k, trajectory_recall, final_answer_recall, precision
- Compare against harness-1 baseline
